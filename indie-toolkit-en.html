Indie Toolkit

A Unity editor toolkit for a small 3D game team: the tools your artists, designers and sound designers need every day, built once and carried into every project you make from now on. You design it like a real tool, starting from the people who will use it. Milestones are assigned one at a time.

Final delivery Wed, January 27Individual project, group analysisUnity 3D projects only

The project

In every game you make, someone builds the same things again: a way to place props, a quick blockout, a check that nothing is missing in the scene. A tools programmer builds them once, makes them easy to use for people who do not write code, and reuses them in the next project.

You build a Unity package with a set of editor tools for a small indie team working on a 3D game. Some tools are the same for everyone. One is chosen by you, for a role in your own team, after talking to the people in that role.

How it works

  1. Analyze who will use the toolkit: the roles in an indie team and what slows them down in the editor.
  2. Write what each of them needs as user stories, and turn them into features.
  3. Build the core tools, milestone by milestone.
  4. Add one tool for a role of your choice, backed by your own analysis.
  5. Release the package so that any Unity project can install it from Git.

Inspired by

The toolkit takes small, simplified pieces from tools used in the industry. You do not copy them: you study what they do and build your own minimal version.

Odin Inspector

Attributes that turn a plain inspector into a clear, safe interface for designers.

ProBuilder

Quick blockout shapes, without the full mesh editing.

Unreal Engine

Foliage painting and cube-grid blockout, reduced to the essentials.

Creative freedom

Interface, shortcuts and workflow are up to you, as long as every feature does what is described. Indie Toolkit is the name of the project: give your package its own name.

Users

A tool is good only if someone uses it. Your users are the people you work with in a team: their needs decide what you build.

From people to features

  1. Stakeholders: who uses the tool, and what they do in the editor.
  2. User stories: one need per line, in the form As a … I want … so that …
  3. Features: what the tool must do to satisfy each story, and how you will check it works.
  4. Priority: how many roles it helps, how much it costs, how risky it is.
As a level designer
I want to see the player's height and jump arc in the scene
so that I can check a platform is reachable without entering Play mode.

The core features come from the teacher's analysis, shown in class as a worked example. You apply the same method, as a class, to find the role features. An analysis is a hypothesis until a real user confirms it: interview students from the courses of those roles, ask what slows them down in Unity, and write down what they said.

Three levels: core for everyone, role at least one chosen by you, extra for a higher grade.

Reverse engineering analysis

For every core feature covered in a milestone, the class writes together a reverse engineering analysis of its reference tool, in a shared repository. Each of you states in your own README what you keep and what you cut compared to the reference.

Role features role

The analysis is a group effort: the class splits the roles, interviews at least one student for each role and writes together a catalog of user stories and feature proposals, in the shared repository.

The choice is individual: each of you picks at least three proposals from the catalog. The teacher picks with you the one to build, based on the estimated workload. Big ideas are welcome: they can be scaled down.

Then you plan it: you decide in which milestones you build each part. Keep this table in your README, one row per proposal, and update it at every milestone with what you planned and what you actually did.

Technical requirements

  • Unity 6.3 LTS, 3D project.
  • The toolkit is a package with its own package.json, installable from Git through the Package Manager.
  • Code split into a Runtime and an Editor assembly definition. The Runtime assembly never references UnityEditor: a build of a game that uses your toolkit must compile.
  • All the math (placement, spacing, grid snap, mesh generation) lives in static classes with no editor code, called by the tools.
  • Every tool supports Undo.
  • Git repository, with a tag for every delivery.
  • A README with: what the toolkit does, how to install it, how to use each tool, the choices you made.
  • AI tools are allowed if declared in the README. You must be able to explain and change any line of your code.

Milestones

Each milestone is delivered with a Git tag by 12:00 on the Wednesday shown, and discussed in class the same afternoon. The details of each milestone are given when it is assigned.

Every milestone includes the reverse engineering analysis of each core feature it asks for, in the shared repository: this is the group part, graded for the whole class and adjusted by each person's visible contribution in its history.

From M2 on, every milestone also includes the parts of your role feature that your plan puts there, and the plan table updated.
