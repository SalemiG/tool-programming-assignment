Indie Toolkit

Un toolkit di editor per Unity pensato per un piccolo team che sviluppa un gioco 3D: gli strumenti che artisti, designer e sound designer usano ogni giorno, costruiti una volta e portati in ogni progetto che farete da qui in avanti. Lo progettate come un tool vero, partendo dalle persone che lo useranno. Le milestone vengono assegnate una alla volta.

Il progetto

In ogni gioco qualcuno rifà sempre le stesse cose: un modo per piazzare gli oggetti, un blockout veloce, un controllo che in scena non manchi niente. Un tools programmer le costruisce una volta, le rende facili da usare per chi non scrive codice e le riusa nel progetto successivo.

Costruite un package Unity con una serie di tool di editor per un piccolo team indie che lavora a un gioco 3D. Alcuni tool sono uguali per tutti. Uno lo scegliete voi, per un ruolo del vostro team, dopo aver parlato con chi ricopre quel ruolo.

Come funziona

  1. Analizzate chi userà il toolkit: i ruoli di un team indie e cosa li rallenta nell'editor.
  2. Scrivete le esigenze di ciascuno come user story e trasformatele in feature.
  3. Costruite i tool comuni, una milestone alla volta.
  4. Aggiungete un tool per un ruolo a vostra scelta, motivato dalla vostra analisi.
  5. Pubblicate il package, in modo che qualsiasi progetto Unity possa installarlo da Git.

Ispirato a

Il toolkit prende pezzi piccoli e semplificati da strumenti usati nell'industria. Non li copiate: studiate cosa fanno e ne costruite una vostra versione minima.

Odin Inspector

Attributi che trasformano un inspector qualsiasi in un'interfaccia chiara e sicura per i designer.

ProBuilder

Forme di blockout veloci, senza la modellazione completa.

Unreal Engine

Pittura del foliage e blockout su griglia (cube grid), ridotti all'essenziale.

Libertà di realizzazione

Interfaccia, scorciatoie e flusso di lavoro li decidete voi, purché ogni feature faccia quello che è descritto. Indie Toolkit è il nome del progetto: date al vostro package un nome vostro.

Dalle persone alle feature

  1. Stakeholder: chi usa il tool e cosa fa nell'editor.
  2. User story: un'esigenza per riga, nella forma Come … voglio … per …
  3. Feature: cosa deve fare il tool per soddisfare ogni storia, e come verificherete che funziona.
  4. Priorità: quanti ruoli aiuta, quanto costa, quanto è rischiosa.

Per ogni feature base trattata in una milestone, la classe scrive insieme una documentazione di analisi di reverse engineering del tool di riferimento, in un repository condiviso. Ognuno indica nel proprio README cosa tiene e cosa taglia rispetto al riferimento.

Feature di ruolo ruolo

L'analisi è di gruppo: la classe si divide i ruoli, intervista almeno uno studente per ogni ruolo e scrive insieme un catalogo di user story e proposte di feature, nel repository condiviso.

La scelta è individuale: ognuno sceglie dal catalogo almeno tre proposte. Il docente sceglie con voi quella da costruire, in base al carico di lavoro stimato. Le idee grandi vanno bene: si possono ridimensionare.

Poi la pianificate voi: decidete in quali milestone costruire ogni parte. Tenete questa tabella nel README, una riga per proposta, e aggiornatela a ogni milestone con cosa avevate previsto e cosa avete fatto davvero.

Requisiti tecnici

  • Unity 6.3 LTS, progetto 3D.
  • Il toolkit è un package con il proprio package.json, installabile da Git tramite il Package Manager.
  • Codice diviso in due assembly definition, Runtime ed Editor. L'assembly Runtime non fa mai riferimento a UnityEditor: la build di un gioco che usa il vostro toolkit deve compilare.
  • Tutta la matematica (piazzamento, spaziatura, snap alla griglia, generazione delle mesh) sta in classi statiche senza codice di editor, chiamate dai tool.
  • Ogni tool supporta l'Undo.
  • Repository Git, con un tag per ogni consegna.
  • Un README con: cosa fa il toolkit, come si installa, come si usa ogni tool, le scelte fatte.
  • Gli strumenti di AI sono ammessi se dichiarati nel README. Dovete saper spiegare e modificare qualsiasi riga del vostro codice.

Milestone

Ogni milestone si consegna con un tag Git entro le 12:00 del mercoledì indicato e si discute in aula lo stesso pomeriggio. Il dettaglio di ogni milestone viene dato quando viene assegnata.

Ogni milestone comprende l'analisi di reverse engineering di ogni feature base che chiede, nel repository condiviso: è la parte di gruppo, e il voto di gruppo tiene conto del contributo di ognuno visibile nella cronologia.

Dalla M2 in poi, ogni milestone comprende anche le parti della feature di ruolo che il vostro piano mette lì, e la tabella del piano aggiornata.
